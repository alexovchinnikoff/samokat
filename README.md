### **Тестирование приложения Яндекс Самокат (сервис для аренды электросамоката).**

В рамках проекта тестировались веб- и мобильные версии приложения, API, база данных. Также реализована автоматизация тестовых сценариев для API.

**Анализ ТЗ:**

ТЗ условно разбито на 4 основных блока:

* Функциональное тестирование веб-приложения (функциональность «Сделать заказ»)

* Ретест багов в мобильном приложении и регрессионное тестирование мобильного приложения по готовым тест-кейсам

* проверка работы базы данных

* автоматизация тестового сценария

**Подход:**

При составлении примерного плана тестирования (по 1 неделе на блок задач), на основании требований, ввиду объема задания, сжатых сроков, с учетом рисков нестабильной работы тестового стенда, было принято решение не тратить время на оформление декомпозированных требований в mind-map, составив черновой вариант для работы и при необходимости приложить к тестовой документации на завершающих этапах.

Заключение:

[Блокирующий баг](https://docs.google.com/spreadsheets/d/1RWuOT-mfPuxCKkwZBN_kiwsMZF6Fnzkr/edit?gid=766036361#gid=766036361&range=A13) блокирует основную функциональность сделать заказ в браузере Chrome. Самые критичные баги с точки зрения пользовательского сценария, касаются возможности сделать заказ с некорректным номером телефона. Этот баг более критичен, т.к. в отличие от ошибок с валидацией полей адрес и дата заказа, при которых заказ скорее всего не будет взят курьером в работу, при указании некорректного номера заказ будет принят курьером, но, например, при ошибке в адресе, курьер не сможет уточнить адрес и заказ будет не доставлен или отменен в последний момент. С точки зрения надежности критичные баги касаются работы API в части возможности создания заказов с некорректными параметрами и которые вызывают внутреннюю ошибку сервера, что может привести к потере данных.

Наиболее хитрой видится зона в части соответствия требований фронтэнда и бэкэнда к обязательности заполнения полей формы «Про аренду».

Функциональность не готова к релизу, т.к. есть блокирующие и критические баги. Также необходимо провести не проведенные проверки.

Заключение:

Самый критичный баг — это постоянная синяя точка во вкладке «Мои», т.к. курьер может забыть про взятый заказ и вспомнит о нем, только когда появится уведомление о сроках заказа, в котором есть другой баг, возникающий при тапе на уведомлении. Остальные критичные баги тоже влияют на функциональность (например, неполный адрес), но курьер может его уточнить, позвонив по телефону.

Несмотря на отсутствие багов, явно блокирующих прохождение сценария, считаю невозможным выпуск в релиз до устранения критических багов. После устранения считаю целесообразным ретест и регрессионное тестирование.

**3. Работа с базой данных PostgreSQL**

**Задача:**

* Проверить, отображается ли созданный заказ в базе данных.

* Убедиться, что в базе данных статусы заказов записываются корректно.

**Подготовка:**

* Анализ карты-структуры базы данных

* Подключился к базе с помощью специальной команды и пароля.

* Посмотрел с помощью команд bash что содержит база данных.

* Отметил в требованиях у psql особенность: если таблица в базе данных с большой буквы, то её в запросе нужно брать в кавычки. Например, select \* from "Orders".

**Реализация:**
Составил запрос, который сначала выводит список логинов курьеров с количеством их заказов в статусе «В доставке» (поле inDelivery = true).

[Ссылка](https://drive.google.com/file/d/1YWw-7yo6oHZ99ZCIcLOQnfVjEGZ7_Ssg/view?usp=drive_link)

С учетом того, что статусы определяются по следующему правилу:

    Если поле finished == true, то вывести статус 2. Если поле canсelled == true, то вывести статус -1. Если поле inDelivery == true, то вывести статус 1. Для остальных случаев вывести 0.

**4. Автоматизация теста к API**

**Задача:**

Автоматизировать сценарий, который подготовили коллеги-тестировщики:

1.  Клиент создает заказ.
2.  Проверяется, что по треку заказа можно получить данные о заказе.

**Анализ:**

Для реализации решено использовать шаги:

1. Выполнить запрос на создание заказа.

2. Сохранить номер трека заказа.

3. Выполнить запрос на получение заказа по треку заказа.

4. Проверить, что код ответа равен 200.
